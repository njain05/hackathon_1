# CLAUDE.md

**Always read context.md and progress.md before starting work, and update progress.md after every completed step.**

## What this is
A college timetable web app that works for any college. Admins generate clash-free timetables, teachers and students view their own schedules, and event organisers book seminar halls and auditoriums with digital approval. See `context.md` for the problem, the data model and the rules.

## Stack
- **frontend/**: Next.js 16 (App Router, TypeScript) + Tailwind CSS v4. Deployed on Vercel.
- **backend/**: Python 3.14.8 (Homebrew) + FastAPI + Google OR-Tools CP-SAT. Deployed on Render.
- **backend/solver/**: the timetable solver as its own module. College data goes in, a timetable comes out.
- (Stage 2) Claude chatbot, called **only from the backend** with tool use.

## Run commands
Backend (http://localhost:8000):
```bash
cd backend
/opt/homebrew/bin/python3.14 -m venv .venv && .venv/bin/pip install -r requirements.txt   # first time
cp .env.example .env                                                # first time
.venv/bin/uvicorn app.main:app --reload --port 8000
```
Frontend (http://localhost:3000):
```bash
cd frontend
npm install                               # first time
cp .env.local.example .env.local          # first time
npm run dev
```
Backend tests: `cd backend && .venv/bin/pip install -r requirements-dev.txt && .venv/bin/python -m pytest -q`
Frontend checks: `cd frontend && npm run lint && npm run build`
End-to-end (real browser): `cd frontend && npx playwright install chromium && npm run e2e` (starts the servers if they aren't running)

## Environment variables

|---|---|---|

| backend | `FRONTEND_ORIGINS` | Comma-separated CORS origins |

## Coding rules
1. **Secrets live only in `.env` files** (and Vercel/Render settings). Never in code or commits. Never put an API key in a `NEXT_PUBLIC_` variable.
2. **Keep the solver pure.** `backend/solver/` takes Pydantic models in and returns a timetable. No FastAPI, HTTP or database code there.
3. **Hard rules are constraints. Soft rules are weighted penalties** in the objective. Never relax a hard rule to get a solution. Report infeasibility clearly instead.
4. **Generic, not hard-coded.** Days, periods, lunch break, departments and so on all come from data. Nothing is specific to one college.
5. TypeScript in strict mode with no `any`. Python with type hints.
6. Usability first. An admin must be able to use every screen without help: clear labels, empty states, readable errors.
7. Timetables must be easy to read: a day × period grid, the lunch break visible, colour by subject.
10. **Nothing college-specific in code.** Days, periods, breaks and room types come from data. New college variations are added as optional fields (see context.md, "College variations").
11. Colours only from the theme tokens in `frontend/app/globals.css` (cream, sky, mint, blush, plus navy and ink for contrast). Reusable classes go in `@utility` blocks, not `@layer components` (Tailwind v4). Variables read only via `var()` (like `--color-subject-N`) go in `:root`, because Tailwind drops unused `@theme` variables. If a CSS change doesn't show in dev, restart `npm run dev`.
8. The chatbot never invents schedule data. It calls real backend functions through tool use.
9. Small, working steps. Commit after each one and log it in `progress.md`.
